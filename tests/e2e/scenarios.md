# E2E テストシナリオ — elxea-agent

## 概要

staging 環境（LINE @426vlcyb → elxea-agent-staging Worker）での手動 E2E テストシナリオ。
各シナリオで期待される応答パターンを定義し、動作検証の判定基準とする。

- **テスト対象**: elxea-agent staging Worker
- **テスト実施日**: 2026-03-16（今夕 staging テスト）
- **検証者**: Setaka

---

## シナリオ 1: 商品相談 → 提案 → カートリンク

### 目的
商品問い合わせを受けた際に、ナレッジから正確な商品情報を取得し、
`recommend_product` ツールで Flex Message カードを送信できることを確認する。

### 前提条件
- ナレッジベースに商品データが同期済みであること（`pnpm sync-knowledge` 実行済み）
- `recommend_product` ツールが正常に動作すること

### テスト手順

| ステップ | ユーザー入力 | 期待される応答 | 確認ポイント |
|---------|------------|--------------|------------|
| 1 | `おすすめのお茶を教えてください` | テキスト回答 + Flex Message カード送信 | ① Flex Messageが表示される ② 商品名・価格がナレッジと一致する |
| 2 | `この商品のURLを教えてください` | elxea.jp ドメインの URL を返答 | ③ URL が https://elxea.jp 配下であること |
| 3 | `他のおすすめも見たい` | 別商品カード（最大3件）を提案 | ④ Quick Reply「他の商品も見たい」が表示されること |

### 期待されるツール呼び出し
```
recommend_product({
  products: [
    { name: "...", description: "...", price: "¥X,XXX", product_url: "https://elxea.jp/..." }
  ]
})
```

### 合格基準
- [ ] Flex Message カードが LINE 上で表示される
- [ ] 商品名・価格がナレッジと一致する（捏造なし）
- [ ] URL が https://elxea.jp ドメイン
- [ ] Quick Reply に「詳しく教えて」「他の商品も見たい」「購入方法は？」が表示される

## シナリオ 2: FAQ 質問 → 回答

### 目的
よくある質問（配送・返品・支払いなど）に対してナレッジベースから正確な情報を返し、
グラウンディングルールが守られていることを確認する。

### 前提条件
- system-prompt.ts の基本情報セクションに送料・返品情報が埋め込み済み

### テスト手順

| ステップ | ユーザー入力 | 期待される応答 | 確認ポイント |
|---------|------------|--------------|------------|
| 1 | `送料はいくらですか？` | 「全国一律 500 円（税込）、5,000 円以上で送料無料」 | ① 正確な金額を返すこと |
| 2 | `返品できますか？` | 「到着後 7 日以内、未開封・未使用に限る」 | ② 条件（7日・未開封）を含むこと |
| 3 | `支払い方法は何が使えますか？` | クレジットカード・Apple Pay・Google Pay・Shop Pay の案内 | ③ 複数決済手段を列挙すること |
| 4 | `在庫はありますか？` | 「確認してお返事します」＋エスカレーション | ④ ナレッジにない在庫情報を捏造しないこと |

### 合格基準
- [ ] 送料・返品ルールが system-prompt の埋め込み情報と一致する
- [ ] ナレッジにない情報（在庫等）を回答しない
- [ ] 在庫問い合わせで `escalate_to_human` が呼ばれる（または適切に「確認します」と答える）
- [ ] 絵文字を使用しない

## シナリオ 3: 注文状況確認

### 目的
LINE-Shopify 紐付け済みユーザーが注文状況を確認する際に、
`lookup_my_orders` / `get_order_detail` ツールが正しく動作することを確認する。

### 前提条件
- テストユーザーの LINE ID が `customer_linkages` テーブルに登録済み（または未登録でテスト）

#### パターン A: 紐付けあり
| ステップ | ユーザー入力 | 期待される応答 | 確認ポイント |
|---------|------------|--------------|------------|
| 1 | `注文状況を教えてください` | 直近5件の注文サマリー | ① 注文番号・合計金額・配送状況が表示される |
| 2 | `#1234 の詳細を見たい` | 注文詳細 Flex Message カード | ② Flex Message に商品一覧・追跡番号が含まれる |
| 3 | `追跡番号を教えてください` | 追跡番号・配送会社 URL | ③ 追跡 URL が正しく表示される |

#### パターン B: 紐付けなし
| ステップ | ユーザー入力 | 期待される応答 | 確認ポイント |
|---------|------------|--------------|------------|
| 1 | `注文状況を教えてください` | 「注文番号をお教えください」案内 | ④ 紐付けなしの場合は注文番号入力を促す |

### 合格基準
- [ ] 紐付けありの場合、注文履歴が正しく表示される
- [ ] 注文詳細 Flex Message カードが表示される（`orderCard` 関数）
- [ ] 紐付けなしの場合、適切なフォールバックメッセージが返る
- [ ] Quick Reply に「配送状況を確認」「他の注文も確認」が表示される

## シナリオ 4: エスカレーション発動

### 目的
エスカレーション条件（クレーム・ナレッジ不足・人間要求）に該当する問い合わせで、
`escalate_to_human` ツールが呼ばれ、Slack に通知が送信されることを確認する。

### テスト手順

| ステップ | ユーザー入力 | 期待されるエスカレーション分類 | 確認ポイント |
|---------|------------|--------------------------|------------|
| 1 | `商品が届かないのですが` | `order_trouble` | ① escalate_to_human が呼ばれること |
| 2 | `スタッフに繋いでください` | `human_request` | ② 「確認してお返事します」というメッセージが返ること |
| 3 | `アレルギー反応が出ました` | `health_safety` | ③ Slack 通知が送信されること（SLACK_WEBHOOK_URL 設定時） |
| 4 | `ナレッジにない特殊な質問` | `knowledge_gap` | ④ ナレッジ不足でもエスカレーションが発動すること |

### 期待されるツール呼び出し
```
escalate_to_human({
  reason: "...",
  category: "order_trouble" | "human_request" | "health_safety" | "knowledge_gap" | ...,
  summary: "..."
})
```

### Slack 通知の検証
Slack に以下形式のメッセージが届くことを確認:
```
エスカレーション [分類]
LINE User: Uxxxxxxxxxxxxxxxxxx
分類: [日本語ラベル]
理由: [エスカレーション理由]
会話要約: [会話内容の要約]
```

### 合格基準
- [ ] エスカレーション条件に該当する問い合わせで `escalate_to_human` が呼ばれる
- [ ] 顧客へのメッセージは「確認してお返事しますね」という内容
- [ ] Slack 通知が送信される（設定済みの場合）
- [ ] エスカレーション後の Quick Reply は「はい、お待ちします」のみ

## シナリオ 5: ウェルカムフロー（友だち追加）

### 目的
新規ユーザーが LINE を友だち追加した際に、
ウェルカムメッセージと Quick Reply が正しく表示されることを確認する。

### テスト手順

| ステップ | アクション | 期待される応答 | 確認ポイント |
|---------|----------|--------------|------------|
| 1 | LINE でアカウントをブロック → ブロック解除（`follow` イベント発火） | ウェルカムメッセージ + Quick Reply 3件 | ① 挨拶文が表示される ② Quick Reply が3件表示される |

### 期待されるウェルカムメッセージ
```
こんにちは！elxea（エルシア）へようこそ。

鹿児島の生産者から届くお茶やスキンケアについて、何でも気軽に聞いてくださいね。

商品のこと、注文のこと、おすすめが知りたいときなど、お気軽にどうぞ。
```

### 期待される Quick Reply
- 「商品を探す」→ 「おすすめの商品を教えてください」
- 「注文を確認」→ 「注文状況を確認したいです」
- 「お茶について」→ 「どんなお茶がありますか？」

### 合格基準
- [ ] `follow` イベントでウェルカムメッセージが送信される
- [ ] Quick Reply が3件表示される
- [ ] テキストに絵文字が含まれない
- [ ] 2回目以降の `follow`（再フォロー）でも同じメッセージが送信される

## シナリオ 6: ID 紐付けフロー

### 目的
LINE ユーザーと Shopify アカウントの紐付けに関する問い合わせが、
適切に処理されることを確認する。

### 前提条件
- `customer_linkages` テーブルが Supabase に存在すること

### テスト手順

#### パターン A: 紐付け済みユーザー（注文確認でID紐付けを使用）
| ステップ | ユーザー入力 | 期待される応答 | 確認ポイント |
|---------|------------|--------------|------------|
| 1 | `注文確認したい` | 直近注文の一覧表示 | ① `customer_linkages` から Shopify ID を取得できること |
| 2 | 注文詳細を確認 | 正確な注文情報 | ② Firestore の顧客プロファイルが存在する場合は顧客名が挿入されること |

#### パターン B: 未紐付けユーザー
| ステップ | ユーザー入力 | 期待される応答 | 確認ポイント |
|---------|------------|--------------|------------|
| 1 | `注文確認したい` | 「注文番号をお教えください」 | ③ 紐付けなしで適切なフォールバックが動作する |

### 合格基準
- [ ] 紐付け済みユーザーは `customer_linkages` 経由で注文情報を取得できる
- [ ] 未紐付けユーザーには注文番号入力を促すメッセージが返る
- [ ] Firestore プロファイルがある場合はペルソナ対応の会話になる

## テスト実施チェックリスト

### 事前準備
- [ ] staging Worker がデプロイ済みであること（`pnpm deploy:staging`）
- [ ] staging 環境の Webhook 設定が LINE Developers Console で Success 済み

- **Pass**: 合格基準の全項目をクリア
