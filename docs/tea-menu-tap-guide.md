# 購入者向け・選択式お茶メニュー案内（タップ主体）

LINE 上で、購入者が **タップだけ**でお茶の「淹れ方」「味・香り」に辿り着ける案内機能。
番号手打ちは予備。AI 生成を挟まず、Notion Tea Menu List DB（Status=販売中）の中身を
そのまま整形して直返しする（**創作ゼロ・LLM 費用ゼロ・deterministic**）。

- 実装: `src/lib/tea-menu.ts`（データ取得 + 純粋ビルダー + インターセプタ）
- 配線: `src/routes/line.ts` `handleTextMessage` の先頭で `handleTeaMenuFlow` を呼ぶ
- 内部確認ハーネス（read-only・push なし）: `scripts/tea-menu-demo.ts`
- 単体テスト: `tests/unit/tea-menu.test.ts`

## フロー

```
入口発話（リッチメニュー① or 「お茶を調べる」等）
  → 種類選択（緑茶 / 青茶 / 紅茶：Category 列で分類）
    → お茶一覧（quick reply・13超は「次へ」でページング）
      → お茶カード（お茶名・番号）
        → 🌡 温度・抽出時間 ／ 👃 味・香り ／（🍵 楽しみ方＝データがある時のみ）
        → 項目タップで DB の該当項目を整形して直返し（末尾で他の選択肢を再提示）

予備: 5 桁番号を含むメッセージ → 該当お茶カードに直行
```

## 状態を持たない設計（state レス）

会話状態は保持しない。**直近のお茶は quick reply の message テキストに 5 桁番号を
埋め込む**ことで引き回す。タップされた message はユーザー発話として webhook に戻り、
`parseTeaAction` が解釈して次の応答を deterministic に返す。

内部トークン（quick reply の送信テキスト。全角縦棒 `｜` 区切り）:

| 用途 | 送信テキスト例 |
|---|---|
| 一覧（種類・ページ） | `お茶を選ぶ｜緑茶｜1` |
| お茶カード | `このお茶｜11301` |
| 温度・抽出時間 | `淹れ方｜11301` |
| 味・香り | `味と香り｜11301` |
| 楽しみ方 | `楽しみ方｜11301` |
| 種類選び直し | `お茶の種類` |

## データの対応（Notion Tea Menu List）

| 表示 | Notion プロパティ | 備考 |
|---|---|---|
| 5 桁番号（一意） | `Menu Name`（title） | 例 `11301`。表示名ではなく番号が入っている |
| お茶名 | `Menu Name - full`（rich_text） | 例「やぶきたの上煎茶」 |
| 種類（分類） | `Category`（select） | 緑茶 / 青茶 / 紅茶 |
| 販売中フィルタ | `Status`（select）= `販売中` | 現状 30 件 |
| 温度・抽出時間 | `How to Brew`（rich_text） | 自由記述に温度・湯量・秒数を含む。構造化列 `How-to_Temp/Time/Water` は現状空 |
| 味・香り | `Flavor Profile`（multi_select）+ `Menu Description(Short ver.)` | |
| 楽しみ方 | `楽しみ方`（rich_text） | **現状 0 件**。入り次第、自動でカードに選択肢が出る |

- 種類別（2026-07 時点）: 緑茶 12 / 青茶 6 / 紅茶 12 = 30 件。
- データは isolate 内メモリに 10 分 TTL でキャッシュ（タップ毎の Notion 再取得を回避）。

## quick reply 上限（13個/回）への対応

- 一覧は **1 ページ 11 件**（`TEA_LIST_PAGE_SIZE=11`）。残り 2 枠を「次へ」「種類に戻る」に使い、
  1 回の quick reply が **常に 13 個以内**に収まる。
- 12 件ある緑茶・紅茶は 2 ページに分割（1 ページ目 11 件＋「次へ」＋「種類に戻る」＝13、
  2 ページ目 残り 1 件＋「種類に戻る」）。
- 種類選択・カード・各回答の quick reply も全て 13 以内（単体テストで検証済み）。

## QR リンク仕様（番号入りメッセージの自動送信）

QR 画像そのものの生成は本タスクのスコープ外。ここでは **QR に埋め込む URL の仕様**を定義する。

LINE の「メッセージ送信リンク（oaMessage スキーム）」を使う。ユーザーが QR を読むと、
その OA とのトーク画面が開き、指定テキスト（＝5 桁番号）が**送信可能な状態でセット**される
（送信操作はユーザーが行う）。番号が送られると本機能の「番号直指定」でお茶カードに直行する。

```
https://line.me/R/oaMessage/{OA_BASIC_ID}/?{TEXT}
```

- `{OA_BASIC_ID}`: LINE 公式アカウントのベーシック ID（`@` を含む）
  - staging（テスト OA）: `@426vlcyb`
  - 本番 OA: `@307tzhkw`
- `{TEXT}`: 送信するメッセージ本文。ここに **5 桁のメニュー番号**（＝Notion `Menu Name`）を入れる。
  - 5 桁数字は ASCII のため URL エンコード不要。日本語を足す場合は `encodeURIComponent` 必須。

例（staging・「やぶきたの上煎茶」= 11301 に直行させる QR に埋め込む URL）:

```
https://line.me/R/oaMessage/@426vlcyb/?11301
```

補足:
- 番号のみのメッセージ（`^\d{5}$`）は、一致すればカード表示、不一致なら**正直に「見つかりませんでした」
  と案内**して種類選択を出す（創作しない）。
- 文中に 5 桁が混ざる一般発話（例「郵便番号は 12345」）は、**既知のお茶番号に一致した時だけ**
  カードにし、一致しなければ AI 自由対話へ素通りさせる（誤爆で自由対話を奪わない）。

## 既存フローとの非干渉

`handleTeaMenuFlow` は **限定トリガーのみ**反応する:
- 入口発話（完全一致）/ `お茶を選ぶ｜…` 等の内部トークン / 5 桁のみ / 既知 5 桁を含む発話。

上記以外は `parseTeaAction` が `null` を返し、Notion も叩かず即 `false`（＝素通り）。
好み診断・注文照会・自由な淹れ方質問・オンボーディング・フィードバック等の既存経路は
一切変更しない。AI 自由対話（`runAgent`）へはいつでも移行できる。

### インターセプタ順序（回帰防止・重要）

`handleTextMessage` では **オンボーディング → フィードバック → tea-menu** の順で呼ぶ
（`src/routes/line.ts`）。理由: フィードバックの「改善希望」タップ後は**次のメッセージが
コメントとして pending 収集**される。ここに 5 桁番号や入口語が混ざると、tea-menu を先に
置くとコメントが横取りされ `message_feedback` 記録と Slack 通知が失われる。よって
pending-state を持つハンドラ（onboarding / feedback）を tea-menu より**先**に置く。
これらの pending トークンは tea トリガーと衝突しないため、後置は安全（単体テストで順序を固定）。

### オーナー認識事項

- **裸の 5 桁メッセージ（`^\d{5}$`）は、未知番号でも tea-menu が横取りする**（＝AI 自由対話に流さず
  「見つかりませんでした」と案内する）。これは番号直指定の予備導線を確実にするための意図的挙動。
  文中に 5 桁が混ざる一般発話は、既知番号一致時のみ反応（未知なら素通り）なので影響しない。

## 入口発話（トリガー）

完全一致のみ起動（自由入力の別文言は AI 対話へ流す）:
- `お茶のおいしい淹れ方を教えてください`（リッチメニュー① `setup-richmenu.ts` の送信テキスト）
- `淹れ方を教えてください`
- `お茶を調べる`
- `お茶メニュー`
- `お茶を選ぶ`
